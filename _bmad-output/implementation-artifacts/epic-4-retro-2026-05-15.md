## What Went Well

1. Scope alignment prevented inherited artifact drift.
   Story 4.1 corrected the stale compliance-oriented Epic 4 framing and made the current model-expansion epic authoritative without overwriting older historical artifacts.

2. The capability registry created a durable expansion point.
   Story 4.2 introduced explicit model/provider metadata, stable helper functions, planned-family entries, and tests that prevent planned candidates from becoming silently runnable.

3. The first rollout stayed production-aligned.
   Story 4.3 promoted `llama` as a Bedrock-backed family alias for local and deployed runtimes. The implementation reused `BedrockAdapter`, Bedrock Converse, existing IAM/model ARN assumptions, and explicit model IDs.

4. Direct-provider evaluation was contained instead of normalized.
   Story 4.4 added `litellm` as exploratory local-only evaluation, with optional dependency guidance, Moonshot/Kimi example configuration, credential checks, API-base validation, and deployed-runtime rejection tests.

5. Documentation and tests converged by the closing story.
   Story 4.5 added a final README verification strategy and strengthened static tests. The story record reports the full suite passing with `make lint` clean after review follow-up.

## Challenges

1. Historical artifacts created ambiguity.
   Older files such as `4-1-governance-foundation-documentation.md`, `4-3-bedrock-guardrails.md`, `4-4-red-team-ci.md`, and `4-5-compliance-dashboard.md` belonged to a previous compliance-oriented numbering scheme. The current workflow had to consistently follow sprint status and the current `epics.md` definition.

2. Most review findings were contract-drift issues.
   Repeated review patches caught README, `.env.example`, project-context, and test wording that lagged behind implementation. This was especially visible when `llama` moved from planned to supported and when `litellm` became exploratory local-only.

3. Optional provider support widened the testing surface.
   LiteLLM introduced dependency, credential, base URL, outbound network, and provider-specific failure modes. The team correctly kept live smoke optional and CI deterministic, but the support surface is now more complex.

4. Some deferred work remains.
   Deferred items include LiteLLM credential guidance for non-Moonshot providers, additional URL path validation, provider-case normalization, some registry/test hygiene, and the older future-DOB behavior in `deploy/app.py`.

5. Live provider verification was intentionally limited.
   Unit and static coverage is strong. Live smoke for Llama, Gemini, and LiteLLM still depends on external access, credentials, optional dependencies, and model grants.

## Key Lessons

1. Provider support is a system contract.
   Adding a provider affects code, tests, README, `.env.example`, deployment assumptions, IAM/model access, project context, and verification guidance.

2. Bedrock-backed family aliases are lower risk than direct-provider deployment changes.
   `llama` succeeded because it reused the existing Bedrock path while making the family boundary explicit.

3. "Supported", "planned", and "exploratory" must remain distinct words.
   The distinction prevents users and future agents from treating metadata or examples as runnable production support.

4. Static tests are valuable for documentation contracts.
   The most common regressions were wording and matrix drift, not only runtime behavior.

5. Historical artifact indexing is now more important.
   Older numbered story files are useful context, but they can mislead workflows unless active artifacts are easy to distinguish.
