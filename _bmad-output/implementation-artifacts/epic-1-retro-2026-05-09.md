## What Went Well

1. Brownfield reality was handled correctly.
   The team stopped trying to force the repo back to the original minimal scaffold and instead validated the actual current project shape. Story 1.1 explicitly preserved `compliance/`, `docs/`, `infra/`, `.vscode/`, and the existing test structure.

2. Runtime boundaries got clearer.
   Story 1.3 extracted provider construction into `model_adapters.py`, reducing `agent.py` to a focused local entrypoint while keeping the deployed runtime independent.

3. Deterministic test coverage became the project's main safety net.
   Story records show targeted static, unit, eval, prompt-parity, and safety-boundary checks. This matters because live model access was not always available.

4. Prompt and configuration contracts were tightened.
   Review feedback from the earlier Story 1.2 artifact identified weak DD/MM/YYYY guidance, insufficient tool-use language, and silent fallback behavior. The current story record shows those issues were addressed.

5. Evidence quality improved across stories.
   Later story records distinguish deterministic validation, live credential checks, and manual VS Code validation instead of treating all acceptance criteria as equally automatable.

## Challenges

1. Planning artifacts and repo state drifted.
   The original Epic 1 framing assumed greenfield scaffold work, but the repo already had substantial implementation and later-epic artifacts. This created risk of inappropriate rewrites.

2. Historical story files caused ambiguity.
   Older files such as `1-2-working-age-in-days-agent.md` and `1-3-vs-code-debug-configuration.md` remain in the implementation folder. The active sprint-status keys were needed to identify the current authoritative story files.

3. Live validation depended on external model access.
   Story 1.2 reports that live Bedrock conversation checks were blocked by revoked access to a legacy Anthropic model. The deterministic behavioral contracts still passed, but the live path remains a separate acceptance concern.

4. Manual VS Code validation could not be completed by the agent environment.
   Story 1.4 validated the JSON contract and README alignment, but F5 breakpoint behavior still requires a human VS Code session.

5. Sprint tracking is slightly inconsistent.
   All Epic 1 stories are `done`, but the `epic-1` status remains `in-progress`. This should be reconciled by the project lead or sprint-status workflow.

## Key Lessons

1. Use sprint-status as the authority for current story identity.
   File history is useful, but duplicate historical story artifacts can mislead retrospectives and implementation agents.

2. Separate deterministic, live, and manual validation explicitly.
   This avoided false confidence and made the remaining acceptance risks visible.

3. Runtime separation is a core product feature, not just an implementation detail.
   The project teaches local Strands development and AgentCore deployment as distinct but aligned paths. The adapter extraction supports that teaching goal.

4. Review findings should update the contract, not just the code.
   The most valuable review follow-ups strengthened tests and story evidence, reducing repeat risk.

5. Brownfield handling needs to be declared early.
   When a story starts from an already-implemented repo, the first task should be context reconciliation, not file creation.
