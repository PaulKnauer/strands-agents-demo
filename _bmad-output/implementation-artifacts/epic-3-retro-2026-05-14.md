## What Went Well

1. README moved from setup guide to project map.
   Story 3.1 delivered a comprehensive README with prerequisites, local setup, AgentCore deployment, project structure, how-it-works explanation, troubleshooting, contributing guidance, and current make targets.

2. Runtime boundaries became easier to inspect.
   Story 3.2 reinforced that `agent.py` is local Strands runtime, `model_adapters.py` is local-only adapter construction, and `deploy/app.py` is the cloud AgentCore runtime using direct Bedrock Converse calls.

3. Review improved the artifacts, not just the code.
   The first code review caught stale README structure, forkability wording, long comment style, and status-history inconsistencies. The re-review caught final sprint-status and Epic 3 aggregate status issues.

4. Validation remained explicit.
   Story 3.2 recorded `make lint` and `make test` results. Final review actions repeated both commands successfully.

5. Epic 2 retro lessons were applied.
   Epic 2 flagged artifact drift, tracking reconciliation, README accuracy, and runtime-boundary clarity as preparation needs for Epic 3. Epic 3 directly addressed those themes.

## Challenges

1. Artifact drift remained the main source of friction.
   Older Story 3.2 artifacts existed under a different title, and sprint status initially showed the current Story 3.2 as backlog. The active story had to explicitly state that `sprint-status.yaml` and `3-2-inline-explanation-and-structure-clarity` were authoritative.

2. Status synchronization required multiple passes.
   The story moved through review and done, then the aggregate `epic-3` key also needed correction to `done` after both stories were complete.

3. Forkability wording needed precision.
   The older "single-file agent" framing no longer matched the actual local/cloud split. Epic 3 clarified that use-case behavior may need updates in both `agent.py` and `deploy/app.py`, while the surrounding scaffolding remains reusable unless dependencies or AWS resources change.

4. Deferred behavior debt surfaced during review.
   Code review found that a future date of birth can produce a negative age in `deploy/app.py`. That behavior predates Epic 3 and was deferred intentionally, but it is now tracked.

## Key Lessons

1. Documentation is part of the implementation contract.
   README examples, project structure, and troubleshooting content must track actual code, tests, and deployment behavior.

2. Runtime-boundary clarity prevents bad future changes.
   Epic 4 provider expansion will be safer because Epic 3 made the local/cloud split explicit.

3. Code review should include story and sprint artifacts.
   The most useful findings were not all code bugs. Several were consistency problems across README, sprint-status, and story records.

4. Active artifacts need a clear authority model.
   Historical story files are useful context, but workflow automation must follow current sprint status and active story keys.

5. Deferred work should be visible and specific.
   The future-DOB negative-age behavior is now tracked with location and rationale rather than buried as review noise.
