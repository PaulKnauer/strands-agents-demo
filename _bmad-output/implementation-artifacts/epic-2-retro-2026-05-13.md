## What Went Well

1. The deployment path became explicit and idempotent.
   Story 2.1 preserved the five-step deployment flow: S3 artifact handling, deployment ZIP construction, IAM role provisioning, AgentCore create/update, and READY polling. Tests lock env validation, endpoint output, IAM scoping, runtime lookup pagination, create/update behavior, and failure diagnostics.

2. Runtime boundaries were protected.
   Story 2.2 made the deployed runtime Bedrock-first and prevented `deploy/app.py` from importing local Strands runtime code. Unsupported deployed provider combinations now fail explicitly instead of silently falling back.

3. Verification became meaningful.
   Story 2.3 moved from "response contains a digit" to a real age-in-days correctness check, explicit response decoding, runtime readiness checks, failure guidance, and a performance budget aligned with live behavior.

4. Live observability was ultimately proven.
   Story 2.3 records CloudWatch `aws/spans` evidence for runtime session `verify-session-80da070f846f4c088aee29dc86e18b32`, including `tool.get_today_date` and the final response `13,208 days`.

5. Observability foundations became repeatable.
   Story 2.4 split CDK-managed observability prerequisites into their own contract: Transaction Search, runtime-role observability permissions, stack outputs, make targets, and non-fatal verifier preflight diagnostics.

6. Review findings materially improved the system.
   Review cycles caught ARM64/x86_64 packaging mismatch, missing READY-state handling, false-positive age matching, stale README output, non-actionable runtime failures, and missing inference-profile IAM support.

## Challenges

1. Live AWS validation exposed several hidden assumptions.
   The deployment initially hit runtime failure modes that deterministic tests could not catch, including incompatible binary artifacts, model access denial, and runtime 500 behavior when Bedrock rejected the configured model.

2. Model assumptions shifted during the epic.
   Earlier documentation and story records referenced Anthropic model IDs. Live validation pushed the project toward Amazon Nova Micro inference profiles and required IAM support for inference-profile resources.

3. Observability was harder than "open the console."
   The project needed CDK ownership of Transaction Search and runtime-role permissions, plus clear guidance on CloudWatch surfaces and the `aws/spans` evidence path.

4. Story scope expanded because real production proof demanded it.
   Story 2.3 accumulated deployment, teardown, verifier, runtime, IAM, README, and observability fixes before Story 2.4 extracted the foundation contract.

5. Artifact history remains noisy.
   Historical or superseded story files still exist beside the current sprint-status story files. As in Epic 1, sprint-status is the reliable authority, but the folder can mislead a reader.

6. Aggregate sprint status is still inconsistent.
   Epic 2's stories are all done, but the aggregate `epic-2` key remains `in-progress`. This mirrors the Epic 1 tracking inconsistency noted in the previous retro.

## Key Lessons

1. Treat live AWS proof as a different class of evidence.
   Unit tests can lock contracts, but runtime architecture, model access, inference-profile IAM, and managed observability require live validation records.

2. Observability prerequisites belong in infrastructure code.
   Console discovery is useful for diagnosis, but repeatable onboarding requires CDK-managed Transaction Search, runtime-role permissions, and documented stack outputs.

3. Deployed model support must be explicit.
   Local provider flexibility does not imply deployed AgentCore support. Bedrock-first deployment boundaries need validation, docs, and failure messages.

4. Review findings should be folded into the story record.
   Epic 2's strongest artifacts are the ones that include review findings, decisions, deferred work, and live validation updates.

5. The README is part of the acceptance surface.
   The deployment path succeeds only when commands, expected output, troubleshooting, and console inspection steps match the actual system.
